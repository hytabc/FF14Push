# Engineering Taste

- Wants derived/displayed values to be computed once server-side as a single source of truth rather than reimplemented in the frontend: for the hero panel's per-stat breakdown explicitly chose the backend to emit the structured intermediate quantities over mirroring the stats computation in the frontend, so the shown numbers stay "100% 同源" with actual settlement and "后端改公式不会漂移" (a backend formula change can never desync the display). Rejects duplicating backend aggregation logic in the frontend even when the backend change is larger; favors a design where the backend's settlement path and the explanation path are the same computation. Confidence: 0.55
- Prefers status/monitoring panels to fetch data on demand rather than auto-poll: for the admin online-players view chose a manual 「刷新」 button over the agent's recommended automatic ~10s frontend polling (auto-fetching only once on first entering the tab). Favors avoiding recurring background requests for data that is only useful while the operator is actually viewing it. Confidence: 0.45
- Wants database protection automated and version-managed rather than manual: a recurring job that dumps the whole database's *content* (a logical `pg_dump`, explicitly preferred over copying raw data files for portability/transactional consistency) and packs it into a compressed archive (`tar.gz` with a `dump.sql` + `manifest.txt`), plus a bounded retention policy that keeps the most recent N archives and auto-prunes older ones. Chose to run it as a service inside the project's own docker-compose orchestration ("内置 compose 备份服务") over host-side cron/systemd, so the safeguard ships with the deployment and needs no extra host configuration, and expects the tunable knobs (output dir / interval hours / keep-count / filename prefix) documented in `.env.example` and the README together with an explicit restore procedure. Confidence: 0.45
- For UI/visual changes, wants the actually rendered result verified, not just green checks: when offered a choice after typecheck/unit-tests/build had already passed, chose to install the browser-automation tooling so the agent could screenshot and inspect the real page (desktop + mobile widths, both data states, console errors, accessibility audit) rather than skipping visual verification or eyeballing it themselves. Prefers the fix loop to run against the real render (visual defects found this way — truncated names, wrapping hints, wrong color tokens — get corrected before hand-off). Confidence: 0.5
- Treats backend compute load under multiplayer as a problem to solve by offloading to the client where reasonable — explicitly open to moving certain computation to client-side execution to relieve the server, but only paired with anti-cheat (防作弊) so the trust boundary is preserved (the client may do work, but its results must still be safeguarded). Confidence: 0.5
- Wants network payloads compressed to relieve bandwidth pressure in multiplayer, and treats large/frequent API traffic (e.g. battle session report endpoints) as something to optimize rather than send verbatim. Confidence: 0.5
- Runs the project on a tightly resource-constrained production server (small host, ~2 cores / 2 GB, docker-compose deployment) and treats server CPU/memory efficiency as an ongoing design requirement rather than a one-off task — proactively raises it ("由于当前服务器CPU和内存紧凑，也需要考虑针对其对应的优化") and expects optimizations prioritized by benefit for a small machine (fewer uvicorn workers, per-process connection-pool profiles, lower refresh cadence, composer/PG memory limits, bounded caches, retention/cleanup for ever-growing tables). Confidence: 0.5
- Treats a reported defect as one instance of a bug class and expects the fix to cover the whole class: when handed a single bad case (a fishing legend whose 白昼 gate conflicted with its 深夜-only prerequisite) explicitly asked to both fix it and audit whether anything else has the same problem ("修复并排查是否还有其他鱼存在类似问题"). Wants a full sweep of the affected data/logic plus a guard so the class can't silently return, rather than a narrow patch of only the reported entry. Confidence: 0.6
- Wants standing/recurring project conventions codified into the repo's `AGENT.md` so they apply automatically instead of being restated each request — explicitly asked both the "always reply in Chinese" rule and the "every change must add a changelog note" rule be written into AGENT.md, "防止我每次提问都要重复该内容" and "防止功能遗落". Treats a repeated instruction as a signal it belongs in the agent doc, not just in the current conversation. Confidence: 0.6
- Expects the agent to read the repo's `AGENT.md` at the START of every task, each time, to pick up the latest project design and code/collaboration requirements — stated as a standing rule ("后续每次都需要读取agent.md来获取最新项目设计和代码对话要求") rather than something to do only when first oriented. AGENT.md is treated as the authoritative, living source of current conventions, so it should be re-read per task instead of relying on earlier context. Confidence: 0.7
- Wants a repo-root changelog (`CHANGELOG.md`) to be the single source of truth for the displayed version number and the app's update announcement, so one edit propagates to both rather than maintaining a second copy of the data. Derived/duplicated version state should be read from that one file (parsed/inlined at build time) rather than hard-coded separately. Confidence: 0.5
- Wants every content change accompanied by a concise, human-readable update note — "尽量一句话表述清晰" — appended under the latest version entry, treating a missing summary as an incompleteness; the changelog stays directly editable by the user (manual entries must never be overwritten/reordered by the agent), and a new version is published by adding a `## Vx.y.z — date` entry and syncing the engineering version fields. Confidence: 0.55
- Treats the changelog/update announcement as strictly player-facing copy and forbids any internal/implementation detail in it ("更新公告是面向玩家的，禁止在公告内书写任何关于文件变动和不应被玩家看到的更新内容"): only player-perceivable changes (new gameplay, numbers/balance, UI/UX, bug fixes) written in player language, never file names, paths, class/function names, DB migrations, dependencies, scripts, tests, refactors, docs or deployment notes — purely internal technical changes are omitted from the file entirely. Non-player-facing maintainer notes/instructions belong above all version headings so the parser never surfaces them in the announcement, and the rule is codified into AGENT.md plus a guard test asserting announcement entries contain no internal identifiers. Confidence: 0.6
- Ties changelog organization to the git commit boundary: when cutting a new version, treats any changelog notes not yet committed to git as belonging to that release and expects the agent to move them under the newly created version entry ("更新日志未提交git的都挪到v1.0.2里"), rather than leaving them under the previous version. Uncommitted entries accumulate toward the next version. Confidence: 0.45
