# Security Taste
- Wants account bans (封号) enforced as a hard, server-side cut-off: banned users cannot log in and any already-authenticated banned session is forcibly logged out, rather than merely blocking the next login. Confidence: 0.6
- Prefers the frontend to surface no meaningful/descriptive text for security-sensitive states (e.g. banned accounts) — deliberately vague UI copy to prevent users from reverse-engineering the underlying logic. Confidence: 0.55
- Treats XSS/injection protection as a baseline requirement to build into new features (security hardening expected by default, not as an afterthought). Confidence: 0.55
- Wants a ban/penalty to extend across all public-facing surfaces, not just authentication: banned players must also be hidden from shared views like the leaderboard, not merely blocked from logging in. Confidence: 0.5
- Treats the client as untrusted for economy/reward state: currency and reward amounts must be computed and granted server-side, with any client-supplied amount ignored (explicitly raised as "防止兑换码本地修改数据导致金币无限"), and after a rewarded action the client should re-fetch authoritative state rather than patch local values from the response. Confidence: 0.7
- Wants time-based game logic to be server-authoritative: client-reported timing (elapsed time, browser/animation-frame timestamps) must never be trusted to grant rewards, kill credits, or fight windows, because users can tamper with browser speed / clock to accelerate progress ("防止用户通过修改浏览器速度实现游戏加速逻辑"). Expects the server to compute windows from its own recorded clock only, with client timing kept as reference, and guards/tests added so a forged client time cannot buy credit. Confidence: 0.6
- Wants explicit anti-abuse protection against multi-accounting (防多开) built into the relevant entry points — account-creating (register) and reward (redeem) endpoints — e.g. per-client-IP rate limits and caps on how many accounts from the same IP can claim the same reward, rather than assuming one account per user. Confidence: 0.6
- Wants sensitive account identifiers kept out of public-facing surfaces entirely, and enforced server-side: explicitly asked that chat not display the administrator's ID ("聊天室管理员不显示ID"), and the fix removed the admin login account from the API payload itself (`serialize` returns an empty `username` for admins) rather than only suppressing it in the UI — so the identifier never reaches other players' clients/network responses. Prefers hiding a sensitive field at the source over cosmetic frontend masking. Confidence: 0.5
- Wants anti-abuse rate limiting built into interactive user-generated-content features by default, not (only) on auth/economy endpoints: explicitly required a per-user chat frequency cap to prevent 刷屏 ("聊天具有聊天次数限制（防止刷屏）"). Treats a live UGC surface as needing a spam guard out of the box. Confidence: 0.5
- Wants anti-alt / anti-multi-boxing protection extended from registration/redeem into the economy's gold-laundering channels: friend gold transfers and market (寄售/收购) trades between accounts judged to be the same person must be capped, so an alt cannot funnel gold to the main. Confidence: 0.55
- Wants "same person" determination for anti-abuse to combine device fingerprint AND IP signals jointly rather than either alone, with the browser-derived device id (deliberately stable across different browsers and incognito on the same machine) as the stronger link and IP as a softer/fallback signal. Confidence: 0.5
- Prefers soft enforcement for suspected multi-accounts at the ECONOMY layer — throttle/reduce their quotas (转账 / 交易板额度) rather than banning, so legitimate users sharing a network (dorm/family) and pre-existing multi-accounts are not locked out. That soft stance is scoped to economy quotas: hard enforcement is explicitly wanted on ACCOUNT CREATION (registration) and, per a later request, on live multi-boxing as well — demanded a hard same-user limit on already-logged-in accounts ("需要硬限制已经登录的同一用户下的多个账号"), i.e. cap same-device concurrent-online accounts / force single-session and cut off the extra sessions instead of merely throttling them. Confidence: 0.6
- Tolerates a person having a main plus one alt (roughly 2 accounts per device/person) rather than enforcing a strict one-account-per-person rule. Confidence: 0.45
